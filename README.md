Health checks run every ten minutes (UTC minutes 7, 17, 27, 37, 47 and 57), or manually; destinations exist only in Actions secrets `URL_1` and `URL_2`, and logs expose only numbered results. A manual `test_failure=true` fails check 2 locally without changing secrets. [GitHub notifications](https://docs.github.com/en/actions/concepts/workflows-and-actions/notifications-for-workflow-runs) go to the scheduled workflow's creator, then the last user to edit its cron syntax, or the user who re-enables it; email requires the account's [Actions notification settings](https://docs.github.com/en/subscriptions-and-notifications/how-tos/managing-github-actions-notifications) to enable Email (with optional “Only notify for failed workflows”; the documentation does not promise email is enabled by default). [Personal repositories are watched by their creator by default](https://docs.github.com/en/subscriptions-and-notifications/concepts/about-notifications#default-subscriptions); at setup, the owner's actual Actions preference was verified as “On GitHub, Email (Failed workflows only)”. [Scheduling rules](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule) specify a five-minute minimum, possible high-load delays or dropped runs (especially on the hour; no typical delay or delivery deadline is guaranteed), and automatic disablement after 60 days without repository activity in public repos; a monthly empty commit keeps this repository active while the workflow still runs, but cannot revive a disabled workflow. This is best-effort health checks, not an SLA: missed runs cannot notify, and email delivery is not verified. Disable with `gh workflow disable health.yml --repo 129129w/uptime-check`.
